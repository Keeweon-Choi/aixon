# Task: local review app for continuous human approval (ADR-021, ADR-025, ADR-026)

The owner reviews content before it is published. Build a small **local** review app: a Python server plus one static page. It is not part of the public site and never ships to GitHub Pages.

Read first: `docs/DECISIONS.md` ADR-021/022, `tools/review.py` (incl. `approve_batch`, `approve_record`, `approve_wiki`, `publish`), `tools/public_gate.py` (`read_wiki`, `wiki_approval`, `gate`), `tools/seedtool.py` (`load_graph`, `approval_state`, `review_hash`), `src/lib/predicates.ts` and `src/lib/badges.ts` (Korean predicate sentences and labels to mirror), `review/*.yaml` worksheets (pre-review notes; format in `specs/codex_review_batch.md`), `docs/verification/CROSS_REVIEW.md` §10 (AI cross-review report and `confirm.json` formats; panel approvals look like `review: {by: panel:<release>, method: cross-review, reviewers, audit, report, ...}`).

You may create/edit: `tools/review_server.py`, `tools/review_app/` (static files), `tools/test_review_server.py`, `tests/e2e/review-app.spec.ts` (+ a `playwright.config.ts` change only if needed to run it), `Makefile` (target `review`), `README.md` (new section "검수 화면"). Nothing in `src/`, `data/`, `docs/`. Stdlib + PyYAML only for the server, plain HTML/CSS/JS for the page (no build step, no CDN). No network, no installs.

## Server (`tools/review_server.py`)
- `python tools/review_server.py [--graph a.yaml,b.yaml] [--wiki-dir DIR] [--port 4400] [--by human:<id>]` binds **127.0.0.1 only**, generates a random token at start and prints `http://127.0.0.1:<port>/?token=<token>`.
- `GET /` serves `tools/review_app/index.html` (and its css/js). `GET /api/queue` (token required) returns every reviewable record: graph records of all entity types, claims, `lab_prediction` items, and wiki docs, each with:
  - `id`, `kind` (entity|claim|wiki|item), Korean type label, display title (entity name; claim: Korean sentence built like the site's predicate templates; wiki: title), `state` (`pending` = no approval, `approved`, `stale` = changed after approval, `invalid` = bad signature; plus `approved_by` = the `by` of the approval, human or `panel:<release>`; computed with `seedtool.approval_state` / `public_gate.wiki_approval`), `public` (in a fresh `public_gate.gate(...)` result).
  - details: entities — aliases, summary, fields (names), paper metadata (title, authors, date, venue, arXiv link); claims — predicate, subject/object names, status, confidence, qualifiers, note, evidence list (quote, locator, type, stance, source title + version, `fulltext_url` + `#:~:text=` first words); items — prompt, choices, answer, tolerance, rationale; wiki — status, entity, cited claims, and the MDX source.
  - pre-review: the most recent worksheet entry for this id from `review/*.yaml` (`recommendation`, `notes`, `fix`, worksheet file name).
  - cross-review: from every report `review/cross/<release>/*.yaml` (except `packet.yaml`) that contains this id: reviewer, start, decision, fix, unchecked, and its checks (field, text, verdict, note, sources with url, tier, passage and the status for that url+passage in the release's `confirm.json`, if present). If `tools/cross_review.py` is importable, add its `check_release(...)` problems for this id (empty = passes); it is being built in parallel, so guard the import and omit the field when it is missing.
- `POST /api/decisions` (token required, JSON `{by, decisions: [{id, decision: approve|fix|exclude, note, publish}]}`):
  - refuse with 403 and a Korean message when the server runs inside an AI agent session (same check as `review.py`: `CLAUDECODE`, `AI_AGENT`, any `CODEX_*`), or when `by` is not `human:<id>`.
  - write all decisions to `review/decisions/<UTC timestamp>.yaml` in the worksheet format (decision + note; `fix`/`exclude` are records for the maintainers), then call `review.approve_batch(...)` for the `approve` ones (wiki `publish: true` → published). Return the summary (approved, published, skipped, failed with reasons).
- `POST /api/commit-push` (token required, same agent-session refusal): commit only `review/`, `data/`, `src/content/wiki/` changes with message `review: <n> approved by <by>` and `git push`; return the command output. Refuse if there is nothing to commit.
- Errors are JSON `{error}`; never print the token in logs after start.

## Page (`tools/review_app/index.html`, `app.js`, `app.css`)
Korean UI, readable on a laptop (and usable at 390 px). Left: the queue with filters (state, kind, pre-review recommendation, cross-review pass/fail/none), a search box (id/name), and counts. Right: the selected record — everything above, quotes shown in English with their locator and an "원문 열기" link; pre-review recommendation and notes highlighted; a "교차 검증" block per reviewer (decision, then a table of checks: field, verdict, source link, tier, passage, confirm status; failing or unconfirmed rows highlighted) and the overall pass/fail with problems; decision buttons 승인 / 수정 필요 / 제외, a note field, and for wiki "승인 후 게시". Decisions are kept client-side (also in `localStorage` so a refresh does not lose them) until "결정 기록" sends them; then show the server's summary and reload the queue. Reviewer id (`human:<id>`) is an input remembered in `localStorage` (default from `--by`). A "커밋하고 배포" button calls `/api/commit-push` and shows the output. Show clearly when the server refuses (e.g. started inside an agent session). Keyboard: j/k next/previous item, a/f/x for approve/fix/exclude.

## Tests
- `tools/test_review_server.py` (pytest, server started on a free port against a tmp copy of `tools/fixtures/mini_graph.yaml` + a tiny wiki dir): `/api/queue` without token → 403; with token lists the records with correct states (one pre-approved via `review.approve_record` shows `approved`; editing it afterwards shows `stale`); pre-review notes from a tmp `review/*.yaml` are attached; `POST /api/decisions` while `CLAUDECODE=1` is set in the **server's** environment → 403; with a clean environment (`env` without agent variables) approving one entity and one claim writes fresh approvals, records `exclude` without touching the record, writes a decisions file; a wiki with `publish: true` ends `status: published`. Do not test `commit-push` against a real remote (unit-test the path filter only).
- `tests/e2e/review-app.spec.ts` (Playwright, fixture target): start the server against a tmp copy of the fixture graph/wiki in `beforeAll` (clean env), open the page with the token, pick a pending entity, press 승인, enter `human:e2e-tester`, press 결정 기록, and assert the queue now shows it `approved`. If you cannot run Playwright in your sandbox, write it and mark the run NOT RUN.
