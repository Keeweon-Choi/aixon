# AI 교차 검증 기준

사람 승인(ADR-021) 없이 공개하는 경로는 이것 하나다. 서로 독립인 AI 검증자 두 명이 모두 승인하고, 도구 대조와 표본 감사를 통과한 레코드만 공개한다(ADR-026). 사람 승인은 그대로 쓸 수 있고, 둘 다 있으면 사람 승인이 우선한다.

검증자는 Opus 5.5(High) 이상, 즉 이 프로젝트의 오케스트레이터와 같은 수준의 추론 능력을 가진 모델만 쓴다. 웹을 열 수 있어야 한다.

## 1. 대상과 판정 단위

| 종류 | 필수 항목(`field`) |
|---|---|
| 엔티티 | `name`, `summary`, 있으면 `aliases`·`question`·`formula`·`variants`·`parameters`·`demonstrates`, `classification`(분야·상위 분류), `metadata`(논문: 제목·저자·날짜·학회·식별자) |
| Claim | `relation`(주어·술어·목적어·한정어가 뜻하는 문장), `evidence[i]`(증거 인용마다) |
| 문항 | `prompt`, `answer`, 있으면 `choices`·`tolerance`·`rationale` |
| Wiki | `para:N`(문단마다. 번호는 검증 묶음에 적혀 있다) |

필수 항목마다 판정이 하나 이상 있어야 하고, 도구가 이를 센다. 한 문단에 사실 서술이 여러 개면 서술마다 판정을 따로 단다. 도구는 "항목마다 하나 이상"까지만 볼 수 있으니, 서술마다 다는 것은 검증자가 지킨다.

판정(`verdict`)은 다음 중 하나다.

| 값 | 뜻 | 통과 |
|---|---|---|
| `supported` | 출처 구절이 서술을 문맥째 뒷받침한다 | O |
| `computed` | 수치·수식·유도를 다시 계산해 맞았다. 계산 과정과 결과를 `note`에 적는다 | O |
| `analogy-sourced` | 비유·예시가 사람이 쓴 글에서 왔고 그 글을 찾았다 | O |
| `no-claim` | 사실 서술이 없는 문단(Wiki 전용. 제목만 있는 블록, 실습 삽입 등) | O |
| `unsupported` | 뒷받침하는 출처를 찾지 못했다 | X |
| `wrong` | 출처와 다르다 | X |
| `analogy-unsourced` | 비유·예시의 사람 출처를 찾지 못했다 | X |

## 2. 출처

근거는 이번 검증 중에 실제로 연 웹 자료다. 검증자의 기억, 다른 AI의 답변, 검증 대상인 글 자체는 근거가 아니다. 판정마다 URL, 등급, 원문 구절을 남긴다.

| 등급 | 자료 |
|---|---|
| A (1차) | 해당 논문 원문(arXiv 판·학회 판), 저자의 공식 코드·문서, 저자 기관의 공식 발표 글 |
| B (2차) | 교과서, 서베이 논문, 대학 강의 자료, 해당 내용을 다룬 후속 논문 |
| C (커뮤니티) | 위키백과, 기술 블로그, Stack Overflow·Stack Exchange, Reddit, 포럼 |

- 논문이 무엇을 제안·주장·보고했는지, 실험 수치, 서지 정보(`metadata`, `evidence[i]`)는 A 출처가 있어야 한다.
- 개념 정의와 일반 설명은 A나 B 하나, 또는 서로 다른 사이트의 C 두 개로 통과한다. C 하나만으로는 통과하지 않는다.
- 도구는 위키백과, Stack Exchange 계열, Reddit, Medium, Quora, 개인 블로그 호스팅 같은 도메인을 검증자가 적은 등급과 관계없이 C로 센다. 올려 세지는 않는다.
- 작성자를 확인할 수 없는 글, AI가 만든 것으로 보이는 글(요약 사이트, 자동 생성 블로그, 챗봇 대화 공유 링크)은 출처로 쓰지 않는다.
- 구절은 원문 그대로, 필요한 만큼만 옮긴다(문장 한두 개). 번역해서 적지 않는다.
- 논문은 판 번호까지 적는다. 본문 구절은 전문 URL(`https://arxiv.org/html/1706.03762v7`처럼 데이터의 `fulltext_url` 형식), 제출일 같은 서지 사실은 abs 페이지(`https://arxiv.org/abs/1706.03762v7`)로 적는다. 도구는 데이터에 있는 판의 전문만 캐시로 대조하고 나머지는 직접 내려받는다. 수치는 그 판에서 확인한다.
- 구절은 서술을 문맥 안에서 뒷받침해야 한다. 원문의 조건·가정·단서("We suspect", "in our experiments", "for large values of")가 글에서 빠졌으면 `wrong`이다.

## 3. 지어낸 내용 점검

- 출처 없이 덧붙은 설명은 고치거나 지운다. 특히 저자의 의도·동기, 연구사("처음", "최초"), 업계 관행, "널리 쓰인다" 같은 말을 본다.
- 비유와 이야기형 예시는 사람이 실제로 쓴 글에서 온 것만 쓴다. 글 안에 출처를 밝혀야 하고 판정은 `analogy-sourced`다. 출처를 못 찾으면 `analogy-unsourced`로 떨어진다.
- 계산 예시(작은 행렬로 softmax 값 구하기 등)는 쓸 수 있다. 검증자가 다시 계산해 같은 값이 나와야 한다(`computed`).
- 인용한 논문과 링크는 실제로 있어야 하고 제목·저자·연도가 맞아야 한다.
- 저자가 하지 않은 말을 저자의 말로 쓰지 않는다.

## 4. 정확성

- 수치·수식·유도는 다시 계산한다. 가능하면 코드로 돌리고 결과를 `note`에 남긴다. 반올림 표기까지 맞춘다(0.9548은 "약 0.95").
- 수식 기호, 차원, 첨자가 출처와 같은지 본다.
- 비교("더 빠르다", "더 낫다")에는 비교 대상과 조건(데이터셋, 규모, 지표)이 붙어 있어야 한다.
- 시점에 따라 바뀌는 말("현재 최고 성능", "가장 많이 쓰는")은 날짜와 출처가 없으면 고친다.
- 같은 사실을 엔티티 요약, Claim, Wiki가 서로 다르게 말하지 않는지 본다. 관계 방향(선수 개념, 개선 대상)이 맞는지도 본다.

## 5. 배우는 사람 입장

- 단순화가 틀린 이해로 이어지지 않는지 본다. 예: "Swin은 층마다 창을 옮긴다"는 틀렸다. 연속한 두 블록에서 일반 창과 옮긴 창을 번갈아 쓴다.
- 번역어는 널리 쓰는 말을 쓰고, 처음 나올 때 영어를 함께 적는다. 같은 개념은 같은 번역어로 쓴다.
- 번역하면서 뜻이 바뀌지 않았는지(조동사, 한정어, 부정) 원문과 맞춰 본다.
- 문항은 정답이 하나뿐이어야 하고 오답은 출처 기준으로 분명히 틀려야 한다. 수치 문항의 허용 오차에는 근거가 있어야 한다.

## 6. 저작권

- 인용은 근거를 보이는 데 필요한 짧은 구절만 쓴다(데이터의 `evidence.quote`는 300자 제한, G017).
- 위키백과와 Stack Overflow 글은 CC BY-SA라서 CC BY 4.0인 AIXON 글에 문장째 옮기지 않는다. 내용만 참고해 새로 쓰고 출처를 단다.
- 블로그의 비유는 출처를 밝히고 짧게 옮기거나 풀어 쓴다. 그림은 가져오지 않는다.

## 7. 절차

1. 자동 검사(`make verify`)를 통과한 내용만 올린다.
2. `tools/cross_review.py packet <release>`로 검증 묶음을 만든다. 레코드 내용, 내용 해시, 필수 항목(Wiki는 문단 번호와 본문)이 들어 있다.
3. 검증자 두 명이 따로 검증한다.
   - 서로 다른 세션에서 하고, 서로의 보고서와 사전 검수표(`review/*.yaml`, `review/*.md`)를 보지 않는다. 내려받은 자료와 임시 파일은 검증자마다 따로 정한 폴더에만 둔다(first-release에서 공용 임시 폴더를 함께 써서 서로의 파일 이름이 보였다).
   - 출발점을 다르게 한다. 한 명은 원문 우선(`source-first`): 인용된 논문부터 읽고 글과 대조한다. 다른 한 명은 서술 우선(`claim-first`): 글의 문장마다 웹에서 따로 찾고, 글에 달린 인용은 나중에 본다.
   - 그 레코드를 쓰거나 고친 에이전트는 검증자가 될 수 없다.
   - 확인하지 못한 것은 `unchecked`에 적는다. 하나라도 있으면 그 레코드는 승인할 수 없다.
4. `cross_review.py confirm <release>`가 보고서의 URL을 다시 내려받아 구절이 실제로 있는지 대조한다. 대조에 실패한 출처는 없는 것으로 센다.
5. `cross_review.py check <release>`가 레코드마다 통과 여부를 계산한다. 조건은 두 명 모두 `approve`, 보고서의 해시 = 현재 해시, 필수 항목마다 통과 판정, `supported`·`analogy-sourced` 판정마다 대조된 출처(§2 등급 규칙 포함), 출발점 두 가지가 모두 있음이다.
6. 표본 감사: `cross_review.py sample <release>`가 통과한 레코드 중 10%(최소 3건)를 고른다. 고르는 순서는 보고서 내용으로 정해지므로 사람이 고를 수 없다. 제3의 검증자가 같은 기준으로 보고(`start: audit`), 두 검증자가 놓친 오류가 하나라도 나오면 그 릴리스 결과를 모두 무효로 하고 고친 뒤 처음부터 다시 한다.
7. `cross_review.py approve <release>`가 통과한 레코드에 패널 승인을 쓴다. 유효한 사람 승인이 있는 레코드는 건드리지 않는다. 릴리스마다 커밋 하나로 남긴다.
8. 한 명이라도 `fix`나 `reject`면 고친 뒤 처음부터 다시 검증한다(해시가 바뀐다). 두 번 고쳐도 통과하지 못하거나, 한 명은 승인하고 한 명은 거부했는데 고칠 방향이 정해지지 않으면 사람 검수 대기열로 넘긴다.

공개 빌드도 같은 계산을 다시 한다. 패널 승인이 적힌 레코드라도 보고서, 대조 결과, 감사 중 하나가 맞지 않으면 공개하지 않는다.

## 8. 게시 뒤

- 되돌리기: 그 릴리스의 패널 승인 커밋을 `git revert`하고 push하면 다음 배포에서 빠진다. 레코드 하나만 내릴 때는 그 레코드의 `review`를 지운다.
- 사이트는 "AI 교차 검증"과 "사람 검토"를 구분해 표시하고, 방법론 페이지에 이 기준과 한계를 적는다.
- 매달 `confirm --refresh`를 다시 돌려 사라졌거나 바뀐 출처를 찾는다. 대조가 깨진 레코드는 빠지므로 다시 검증한다.
- 독자가 오류를 알려 온 레코드는 바로 내리고 다시 검증한다.
- 릴리스마다 자동 게시 목록(레코드, 게시일, 보고서 위치)을 운영자에게 보고한다.

## 9. 한계

- 두 검증자가 같은 계열 모델이라 같은 실수를 함께 할 수 있다. 출발점을 다르게 하고 도구 대조와 표본 감사로 줄이지만, 없앨 수는 없다.
- 도구는 구절이 그 페이지에 있는지만 본다. 구절이 서술을 뒷받침하는지는 검증자의 판단이다.
- 로그인이 필요하거나 스크립트로 그리는 페이지(Reddit 일부 등)는 대조가 안 될 수 있다. 그런 출처만 있는 판정은 통과하지 않으니 다른 출처를 찾는다.

## 10. 파일 형식

검증자 보고서 `review/cross/<release>/<검증자 slug>.yaml`:

```yaml
release: first-release
reviewer: agent:opus55-src-1015     # 파일 이름이 slug와 같아야 한다
model: claude-opus-5-5
start: source-first                 # source-first | claim-first | audit
reviewed_at: 2026-10-15
items:
  - id: clm:intro-sdpa
    reviewed_hash: 1a2b3c4d5e6f      # 검증 묶음에 적힌 해시
    decision: approve                # approve | fix | reject
    checks:
      - field: relation
        text: "Attention Is All You Need가 Scaled Dot-Product Attention을 제시했다"
        verdict: supported
        sources:
          - url: https://arxiv.org/abs/1706.03762v7
            tier: A
            passage: 'We call our particular attention "Scaled Dot-Product Attention"'
        note: ""
    unchecked: []
    fix: ""                          # fix·reject일 때 무엇을 어떻게 고칠지와 근거
```

대조 결과 `review/cross/<release>/confirm.json`은 도구가 쓴다(출처마다 `found`·`not-found`·`fetch-failed`, 받은 시각, 본문 sha256). 패널 승인은 레코드의 `review`에 들어간다.

```yaml
review:
  by: panel:first-release
  method: cross-review
  reviewers: [agent:opus55-src-1015, agent:opus55-clm-1015]
  audit: agent:opus55-aud-1015
  at: '2026-10-15'
  decision: approve
  reviewed_hash: 1a2b3c4d5e6f
  report: review/cross/first-release
  note: ""
```
